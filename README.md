# Deep Plate

React + Vite로 만든 서울 식당 탐색·저장·큐레이션 신청 MVP입니다. 기존 랜딩과 Tally 신청 흐름을 유지하면서 미션 8의 **결제 기능**을 추가했습니다.

- 프론트 저장소: https://github.com/leesj2246-debug/deepplate
- 백엔드 저장소: https://github.com/leesj2246-debug/deep-plate-backend
- 기존 운영 랜딩: https://deepplate.vercel.app/

**2026-09-18 현재 결제 변경은 로컬 브랜치 `codex/add-test-payments`에 있습니다. 위 운영 주소에는 아직 새 MVP/결제가 배포되지 않았으며, 제출 완료 URL로 간주하면 안 됩니다.**

## 선택한 고도화 기능과 이유

기존 MVP는 식당 탐색 → 선택적 회원가입/로그인 → 관심 식당 저장 → Tally 큐레이션 신청을 제공합니다. 신청과 결제가 서로 떨어져 있던 한계를 보완하기 위해 **Tally 신청 제출 → 비회원 주문 → 결제 인증 → 서버 승인 → 결과 확인**을 한 흐름으로 연결했습니다.

상품은 `1:1 큐레이션 신청 결제`, 테스트 금액은 **10,000원**입니다. 기존 결제 실습의 과제용 금액이며 실제 판매가격이 아닙니다. 실제 청구·예약·큐레이션 제공은 하지 않습니다. 정기결제, 환불, 가상계좌, Toss 결제 웹훅과 고객 발송은 범위에 포함하지 않습니다.

## 사용자 흐름

1. 랜딩/탐색 메뉴에서 **큐레이션 신청**을 누르고 사이트 안의 Tally 신청서를 작성합니다.
2. Tally가 실제 제출 완료 이벤트를 보내면 제출 ID만 30분 세션에 기록하고 결제 화면으로 이동합니다. 답변 내용은 프론트에 저장하지 않습니다.
3. 상품과 테스트 금액을 확인합니다. 결제에는 회원가입이나 로그인이 필요하지 않습니다.
4. 결제 버튼을 누르면 서버에 상품 ID와 Tally 제출 ID를 보냅니다. 서버는 서명된 Tally 웹훅으로 미리 확인한 제출만 허용하고, 가격과 주문번호를 정해 PostgreSQL에 저장한 뒤 현재 주문 한 건에만 유효한 서명 토큰을 반환합니다.
5. `mock`은 시뮬레이션 승인/취소를 선택합니다. `toss-test`는 토스 테스트 결제창에서 인증합니다.
6. 복귀한 화면은 서버 승인을 기다립니다. 서버가 PAID를 반환한 경우에만 완료로 표시합니다.
7. 신청 결제는 로그인 여부와 관계없이 현재 브라우저 세션에서 해당 주문 결과만 확인합니다. **주문 내역**은 기존 회원 주문 조회에 유지됩니다. 응답이 끊기거나 결과가 불명확하면 같은 주문의 **상태 다시 확인**을 사용합니다.

| 화면 | 기능 |
| --- | --- |
| `/`, `/?apply=1` | 다국어 랜딩과 사이트 내부 Tally 신청 |
| `/places`, `/places/:placeId` | 식당 목록·상세 |
| `/login`, `/saved` | 기존 회원·저장 기능 |
| `/checkout` | 신청 제출 확인 후 로그인 없이 주문 생성·테스트 결제. 직접 접근 시 신청서 안내 |
| `/checkout/success` | 서버 승인 결과 확인, 불확실 결과 재조회 |
| `/checkout/fail` | 취소/실패 복귀 안내. 쿼리값만 보고 DB를 변경하지 않음 |
| `/orders` | 로그인한 회원의 주문 목록·상태 재확인 |

한국어·일본어·영어를 지원합니다. 로딩, API 오류, 빈 주문 내역, 미설정 상태를 각각 표시하며, 모의 결제와 토스 테스트 결제를 구분합니다.

## 로컬 실행

Node.js 22.13 이상과 백엔드의 PostgreSQL 환경이 필요합니다.

```powershell
npm.cmd ci
# .env.example을 참고하여 .env.local에 VITE_API_BASE_URL을 설정합니다.
npm.cmd run dev
```

프론트 환경 변수는 `VITE_API_BASE_URL` 하나입니다. 기본값은 `http://localhost:3001`이며 배포 시에는 공개 백엔드 HTTPS 주소를 넣어야 합니다.

백엔드 저장소에서 `.env.example`을 참고해 설정합니다.

| 서버 환경 변수 | 용도 |
| --- | --- |
| `DATABASE_URL` | PostgreSQL 연결. 로컬 DB 주소를 운영 배포에 사용하지 않음 |
| `JWT_SECRET` | 기존 인증용 비밀키 |
| `FRONTEND_ORIGIN` | 허용할 프론트 주소. 프로토콜·호스트·포트까지 일치 필요 |
| `PAYMENT_MODE` | 기본 `disabled`, 로컬 `mock`, 토스 개발 검증 `toss-test` |
| `TOSS_CLIENT_KEY` | 테스트 공개 키. 서버가 결제 화면에 필요한 값만 반환 |
| `TOSS_SECRET_KEY` | 테스트 시크릿 키. 서버 환경 변수로만 보관 |
| `TALLY_FORM_ID` | 허용할 Tally 폼 ID. 현재 공개 폼은 `ZjAlQe` |
| `TALLY_SIGNING_SECRET` | Tally 웹훅 서명 검증용 비밀값. 서버 환경 변수로만 보관 |

서버의 `npm.cmd run db:deploy`는 `payment_orders`와 검증된 제출 메타데이터용 `curation_submissions` 테이블을 추가합니다. 대상 DB를 먼저 확인하고 적용합니다. 기존 데이터 리셋은 필요하지 않습니다.

토스 키는 같은 상점/종류의 한 세트가 필요합니다. `test_gck_`는 주문서형 위젯, `test_ck_`는 카드/간편결제 결제창을 사용합니다. `live_*` 키는 서버에서 거절합니다. 키를 `VITE_*` 변수, 코드, GitHub에 넣지 않습니다. 로컬 화면 검증에는 Toss 공식 샘플의 공개 테스트 키를 서버 `.env`에서만 사용했으며, 배포 전에는 본인 테스트 상점 키로 교체해야 합니다.

## 기술 선택

- 기존 React/Express 구조를 유지하고 Toss SDK만 추가했습니다. `payment-lab-next`의 흐름을 가져오되 Next 프로젝트 전체를 복제하지 않았습니다.
- Tally의 공식 `Tally.FormLoaded`와 `Tally.FormSubmitted` 메시지를 `https://tally.so`, 현재 iframe, 폼 ID까지 확인합니다. 단순 iframe `load`로 로딩 완료를 오판하지 않으며 제출 ID 외의 답변은 읽거나 브라우저에 저장하지 않습니다.
- 서버의 `/webhooks/tally`가 `Tally-Signature`를 검증하고 제출 ID·폼 ID·이벤트 ID·시각만 저장합니다. 답변 원문은 저장하지 않으며 검증된 제출이 아니면 주문 생성을 거절합니다.
- 외부 새 탭 신청은 안전한 제출 연결 정보가 없어 제거했습니다. 브라우저 저장이 일시적으로 실패하면 제출 ID를 메모리에 유지하고 같은 모달에서 결제 진입을 다시 시도합니다.
- 비회원 주문에는 7일 만료 서명 토큰을 발급합니다. 토큰은 URL이나 응답 재조회에 노출하지 않고 sessionStorage에 보관하며 해당 주문 한 건에만 사용할 수 있습니다. 저장한 맛집과 회원 주문 내역은 기존 로그인을 유지합니다.
- 실습의 전역 Map 대신 기존 Prisma/PostgreSQL을 사용합니다. 서버 재시작 뒤에도 주문 상태를 유지하고 회원 또는 비회원 주문 소유권과 고정 금액을 서버에서 검증합니다.
- 주문마다 고정 멱등키와 DB 조건부 잠금을 사용합니다. 같은 결제의 동시 승인·재시도는 같은 주문으로 처리합니다.
- 결제사 타임아웃은 즉시 실패 처리하지 않습니다. 서버가 보관한 결제키로 재조회합니다. 시크릿 키는 서버에만 두고, 주문 목록 응답에서는 결제키와 멱등키를 제외합니다. 결제 인증 직후의 복귀 URL에는 Toss가 발급한 결제키가 전달됩니다.
- 단일 상품과 최대 50건 내역으로 범위를 줄였습니다. 상품·PG 호출·승인 처리를 분리해 추후 상품/제공자/페이지 나누기를 확장할 수 있습니다.

백엔드의 `PAYMENT_FEATURE.md`에 API 계약, 상태 전이, 실패·복구 처리와 운영 한계를 설명했습니다. 위젯 UI는 카드·국내 간편결제를 검사하지만, 직접 API 조작 시 미지원 수단을 PG 승인 전에 차단하는 서버 검사는 이번 범위에 없습니다. 테스트 키만 허용하며 실제 판매 전에는 환불·웹훅·속도 제한·운영자 복구까지 별도 검토해야 합니다.

## 검증과 데모

```powershell
npm.cmd run lint
npm.cmd test
npm.cmd run build
```

프론트 자동 테스트는 검증된 Tally 로드 이벤트, 저장 실패 재시도, 30분 세션 만료, 결제 직접 접근 차단, 비회원 주문 토큰, 버튼 한 번으로 토스 결제창 요청을 포함해 **27개 모두 통과**했습니다. lint와 production build도 통과했습니다. 테스트 대역을 사용한 자동 검사이며 실제 PG 승인 증거를 대신하지 않습니다.

- 성공: 큐레이션 신청 제출 → 로그인 없는 결제 화면 → 시뮬레이션 승인 → 완료
- 취소: 주문 생성 → 취소 흐름 보기 → 취소 안내. 서버에서는 미승인 주문으로 남음
- 실패: 승인 요청 금액 변조 → 서버 거절, 다른 회원 주문 접근 → 404
- 복구: 응답 손실 → 완료로 표시하지 않음 → 같은 주문 상태 재확인
- 입력 검증: 필수값 누락/중복 쿼리 → 승인 요청하지 않음

로컬 브라우저에서 **토스 간편결제로 결제하기** 버튼 한 번으로 Toss sandbox 결제창이 열리고, 간편결제·카드 목록과 테스트 결제 안내가 표시되는 것을 확인했습니다. 결제수단 인증과 서버 sandbox 승인은 실행하지 않았으므로 아직 미검증입니다.

## 제출 전 남은 절차

1. 본인 Toss 테스트 상점 키를 서버에 설정하고 sandbox 성공·취소·실패와 서버 승인을 검증합니다.
2. 백엔드 배포 URL의 `/webhooks/tally`를 Tally Integrations에 연결하고 같은 signing secret을 양쪽에 설정합니다. 이 설정 전에는 서버가 결제 주문을 fail-closed로 차단합니다.
3. 운영용 PostgreSQL/백엔드 주소·환경을 연결하고 추가 마이그레이션을 적용합니다.
4. 프론트에 `VITE_API_BASE_URL`을 설정해 Vercel로 배포합니다.
5. 배포 URL에서 신청 제출, 비회원 결제·결과, 로그인 기반 저장과 기존 Tally를 확인합니다.

현재 로컬 구현·검증과 운영 배포 상태는 [인수인계](docs/HANDOFF.md)를 확인합니다.
